## 2. Bootstrap path and why
The path is shim, then `schema.sql`, then **all 63 migrations replayed once on top**, then a full ledger.
Details are in `app-stack/README.md`. Run by `app-stack/bootstrap/bootstrap_db.py`, which
imports `app.main._parse_sql_statements` and `_file_checksum`, so parsing and checksums match the runner exactly.

1. `db-init/00-supabase-shim.sql`
   - Roles: `anon`, `authenticated` and `service_role` (BYPASSRLS).
   - Extensions: `uuid-ossp` and `pgcrypto` in schema `extensions`, plus the Supabase search_path.
   - `auth.jwt()` reads `current_setting('request.jwt.claims', true)::jsonb`, with the legacy `request.jwt.claim` fallback. `auth.uid()`, `auth.role()` and `auth.email()` are included too.
   - Supabase default grants, which `202606122` later revokes.
2. `schema.sql` loads verbatim and cleanly.
3. The replay runs one transaction per statement and tolerates failures, which is exactly what the pre-ledger runner did on every live boot. A second pass retries only the failed statements:
   - 6 recover. The policy needing `get_current_tenant_id()` succeeds once 20260802 has defined it, and the 5 `CREATE INDEX CONCURRENTLY` statements succeed in autocommit.
   - `202606145` is **HOLD** ("DESTRUCTIVE, NOT YET APPLIED"). It is recorded in the ledger but not run.
4. All 63 files go into `schema_migrations`. On boot the runner logs `0 new … 63 already in ledger` and then `Schema verification passed`.

Why neither pure path:
- **Migrations from zero cannot work.** `202605221` already needs `users` and `tenants`. The base tables and enums were created in the Supabase dashboard and never committed. So `main.py`'s "fresh DB → apply all" branch is dead code for a blank database.
- **`schema.sql` with a baseline would boot but is broken.** `schema.sql` has drifted from the migrations, and the worst gap is `password_reset_requests.reset_token_hash` / `token_expires_at` (202606123). Without those columns, **approving a workspace returns 500**.
- **Other drift.** These items are also missing from `schema.sql`; all of them are now in the evidence files listed below, for F2:
  - the unique index `tenants_workspace_code_uidx`
  - table `quality_audit_reports`, which the ORM maps
  - `sites.project_excellence_status` and `sites.financial_closure_status`
  - `project_reviews.qa_reports_viewed_by_project_at`
  - `area_sqft` is still `int`; 20260801 changed it to numeric
  - the columns dropped by 20260815 are still present
  - every RLS enable and policy, plus `current_tenant_id()`

Evidence is in `app-stack/run/bootstrap/`: `migration-replay.json` (per file, every failure and its second-pass result), `drift-schema-sql-vs-migrations.json`, and `catalog-final.json`.

14 failures remain, all harmless:
- objects that `schema.sql` already creates
- live-only objects with no definition in the repo: `pipeline_summary`, `stuck_sites`, `handle_new_auth_user()`
- the retired `project_excellence_items` table, which calls `public.uuid_generate_v4()`
- an index on the never-created `project_budget_items`

Upstream bugs found while replaying (for F2/F5):
- `202606231`'s DO block queries `pg_policy.schemaname`, which does not exist, so it fails everywhere.
- The runner can never apply `CREATE INDEX CONCURRENTLY` (202606133) because it wraps every statement in a transaction.

**Platform admin**
- Health: 200 / 200.
- Platform-admin login: wrong password → 401, correct → 200 with an admin JWT.

**Workspace request and approval**
- `POST /tenancy/request-workspace` → 201 `pending`.
- `GET /tenancy/requests` lists it.
- `POST /tenancy/requests/{id}/approve` → 200 with `workspace_code` (`SMOKER-…`), seat_limit 50, and a one-time setup code. A second approve → 409.

**Workspace-code authenticity**
The app deliberately has no hard "is this code real" endpoint (anti-enumeration, upstream #84). These are the checks it does have:
- `GET /tenancy/branding?code=` returns the company name for a valid code and `name:null` for an invalid one.
- `POST /auth/login/check` with first-party headers returns `needs_password` for a valid code and `unknown` for an invalid one. Without those headers it returns the opaque `checked`.
- `POST /auth/login` with an invalid code → soft 202 with no token.
- `GET /tenancy/workspace-info` is **authenticated and takes no code**. With the BA session it returns the provisioned code; without a session it returns 401.

**Business admin**
- Setting the password with the setup code (`/auth/password-reset/complete`): wrong code → 403, right code → 200.
- BA login with code, email and password → 200, `role=business_admin`.

**Supervisor**

- While pending, the supervisor's login → 202.

- login/check → `needs_password`; `/auth/password-setup` → 200; login → 200, `role=supervisor`.

**Executive**

## 7. Rate limits
The limiter keeps its counts in process memory, keyed by client IP and path. Limits:

| Endpoint | Limit |
|---|---|
| `request-workspace` | 3 / 300 s |
| `admin/login` | 10 / 300 s |
| `login` | 10 / 60 s |
| `login/check` | 20 / 60 s |
| `password-setup` | 5 / 300 s |
| `password-reset/complete` | 5 / 300 s |
| `password-reset/request` | 5 / 300 s |
| `signup/*` | 5 / 300 s |
| `join` | 10 / 60 s |
| `branding` | 30 / 60 s |

- A smoke run uses 2 calls each on `password-setup` and `password-reset/complete`, so **at most 2 full runs fit in 5 minutes**.
- There is no environment variable to turn the limiter off. Cope operationally: `./stop.sh --apps && ./start.sh`, or `reset-db.sh`, resets every window. Use unique emails and company names per run; the smoke test already does.
- The smoke test prints a clear hint when it gets a 429.

## 8. What F4 must know
- **Provisioning internals** to reuse from the configurator. Keep the platform credential server-side. Everything is in `app/backend/app/services/tenancy_service.py`:
  - `insert_workspace_request(db, company=, admin_email=, team_size=, seat_limit=, source_ip=)` returns the request id and commits.
  - `approve_workspace_request(db, request_id=, admin_name=, city=)` takes a row lock and, in one commit:
    - creates the tenant via `_create_tenant_with_retry`, which uses `_generate_workspace_code(slug)` to build `<SLUG6>-<16 hex>` and retries on unique violations
    - inserts the `users` row with role `business_admin`, active, no password
    - inserts a pre-approved `password_reset_requests` row holding a hash of the **setup token**, valid 30 days
    - inserts `business_admins`
    - marks the request approved and enqueues a `notification_outbox` row
    - returns `{tenant_id, workspace_code, seat_limit, business_admin_id, admin_setup_token, company, admin_email}`
  - `_parse_seat_limit(team_size)` maps team-size strings to seats, e.g. `"11 to 50 users"` → 50.
- **Doing it over HTTP instead:**
  - `POST /api/tenancy/admin/login` returns a **30-minute admin JWT** with `aud=platform-admin`.
  - Send that JWT as `X-Platform-Admin-Key`.
  - `PLATFORM_ADMIN_TOKEN` is **no longer accepted** as a static key (upstream #312).
- **Caveat for F5.** A freshly provisioned BA is active and has no password, so `/auth/password-setup` lets **anyone who knows the email and workspace code set the first password without the setup code**. The UI's login/check → `needs_password` step does exactly that. The setup code is therefore effectively optional; this is an account-claim race.
- **Where module lists and guards live:**
  - **Backend lists**
    - `Module` Literal in `domain/schemas/business_admin.py` and in `domain/schemas/supervisor_codes.py`: `bd, legal, design, project, nso, project_excellence`
    - `services/business_admin_service.py`: `_ORG_MODULES`, and `_SUPERVISOR_ONLY_MODULES={"nso"}`
    - the NSO check in `supervisor_code_service.approve_my_pending_exec`
  - **Backend guards**: `rbac/guards.py` (`require_role`, `require_real_role`, `require_module`); `rbac/roles.py` (observer semantics); `core/deps.py` (`get_current_user` rechecks `is_active` and role on every request, and denies writes for observers).
  - **DB** — 5 module CHECKs:
    - `module_codes.chk_module_codes_module`
    - `supervisor_invite_codes.chk_supervisor_invite_codes_module`
    - `user_module_memberships.chk_user_module_memberships_module`
    - `site_delegations.chk_site_delegations_module`
    - `supervisor_executive_requests_module_check`

    These have drifted: three still allow `payment`, and `site_delegations` also allows `financial_closure` and `quality_audit`, which are not in the Python Literal.
  - **Frontend**
    - `src/modules/shared/workspaceModules.js` (`WORKSPACE_MODULES`)
    - `src/router/{AppRouter.jsx, routes.js, guards.jsx}`; `RequireModule` gates routes on the JWT `module` claim
    - `src/rbac/{roles,permissions,scope}.js`
    - `src/modules/shared/chrome/Sidebar.jsx` for navigation
    - platform admin: `src/modules/admin/AdminPortalPage.jsx`; BA portal: `src/modules/business-admin/`
  - **Login JWT claims** (`core/security.issue_token`): `app_metadata.{role, tenant_id, city, module, module_role, supervisor_id}`. The module is the user's *primary* membership, chosen by `auth_repo.get_primary_membership`.
- **Routing.** The frontend uses **HashRouter**, so a configurator page under the admin portal will be at `/#/admin/...`.
- **Project skills.** `app/.claude/skills/` contains the upstream skills `matrix-bd-modularization` and `matrix-bd-concurrency-audit`, which F4 may want to follow.
- **Docker.** The compose file has no bind mounts. `start.sh` still has the raw-socket fallback, which only triggers if the container sits in `created`/`exited` for 20 s. It did not trigger on the final cycle, now that Docker Desktop is healthy again.
