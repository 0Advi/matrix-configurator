# G1 — AI-agent configurator: report

**Status: done.** `agent-configurator/` provides the Workspace Configurator as 27 operations, with one core behind
two front doors: a CLI (`bin/cfg.mjs`) and a stdio MCP server (`mcp-server.mjs`). An agent can use them to design,
validate and publish a Matrix workspace the same way a human does in the visual configurator. It works on the same
drafts and goes through the same publish path as the in-app portal.

- Tests: `node --test` → **49/49 pass** (~4 s).
- Live end to end: done with the CLI only; the draft was cleaned up afterwards.
- Secrets: none appear in this report.

Progress log: `docs/reports/G1-progress.md`. Screens: `docs/reports/G1-screens/`.

## How drafts stay in sync with the visual configurator
- **One store.** The agent reads and writes the configurator server's `/cfg/state` (:4300, persisted to NocoBase,
  D2). That is the exact v5 blob `{customWs, data}` that the browser hydrates from. The in-app copy (`/#/admin`, :5173)
  reads it through its `/cfg` proxy. The live check confirmed the agent's workspace through both URLs.
- **No clobbering.** Every op is read → change → check → write with **ETag / If-Match**.
  - On a 409 nothing is written. The op returns `conflict` plus the current state, and the agent re-reads and redoes
    the step.
  - A browser tab that saves on a stale ETag gets the 409 itself (its pill shows "Sync conflict"). This is tested
    against the real `web/server.mjs` handler.
  - Local mode (NocoBase down) is refused, so drafts never end up living in one browser only.
- **Merge-around invariant.** Every write is checked to carry all other workspaces byte-identical and in their
  original order; otherwise it is refused. `CFG_PROTECTED_WORKSPACES` makes chosen ids read-only for the agent.
  - It was used live for `ws_aditya_test` (the user's) and `ws_chai_point_retail` (F4b's).
  - Their sha256 fingerprints were the same before and after the whole run (`fa651ec9…`, `c685ce28…`).
- **v5 fidelity.**
  - **Actions v5 has run through v5's own class** (`building-blocks/lib/load-dc.mjs`, the shipped .dc.html):
    `createWorkspace`, `addBuiltin`, the wizard + `wizSave`, `applyToggle`, and the Publish button.
  - **Other edits** (stages, fields, gates, tiers, roll-up, permissions) are plain edits of the same shape.
  - **Findings, diff and manifest** come from `validation.mjs`. A parity test runs 19 mixed ops and asserts after each
    step that:
    - the class's own `findings()`, `diffList()` and `manifest()` are identical;
    - the result matches `workspace.schema.json` and `manifest.schema.json`;
    - there are zero v5 error findings, except on the one explicit `allow_new_findings` partial step.
- **Deliberate deviations (display strings only).**
  - Real dates are used in `created` and in the publish history line (`05 Oct 2026 · agent:<name>`); v5 hard-codes
    `03 Oct 2026` and `platform:ops@matrix.io`.
  - A custom refusal message passed to `add_custom_module` is stored with `touched: true` so it is kept.
  - Ids continue past the highest id already in the blob, so they cannot collide.

## Ops (operaton-plat mapping)
| Op | Notes | operaton-plat `matrix.py` |
|---|---|---|
| `list_workspaces`, `show_workspace`, `catalogue` | summary in plain words; manifest optional; built-ins, wizard/workspace templates, vocabularies, app-readable hint formats | `op_show`, `op_catalogue` |
| `create_workspace`, `delete_workspace`* | empty / Blue Tokai template / production Matrix-bd flow | `op_reset` |
| `add_builtin_module`, `enable_module`, `disable_module`, `remove_module`* | v5 refusal when dependents wait; `also_disable_dependents` cascade; remove with `drop_conditions` / `inherit_gate` | `op_add_module(from_catalogue)`, `op_remove_module` (rewiring) |
| `add_custom_module`, `update_module` | whole v5 wizard in one call; key checked against v5 rules and the app's built-in keys/aliases | `op_add_module(tasks)` |
| `set_gate` | `conditions` + all/any, or the `starts_after` shorthand; refuses cycles, dead gates and unreachable outcomes (lists the reachable ones) | `op_set_after` |
| `add_stage`, `update_stage`, `remove_stage`* | custom modules only (v5 locks built-in stages) | `op_add/update/remove_task` |
| `add_field`, `update_field`, `remove_field`* | affects-outcome; local port of the app's hint parser warns about `unparsed_hint` immediately | `op_add_field` |
| `set_tiers`, `set_approvers`, `set_outcome`, `set_permission` | supervisor-only / executive / BA sign-off / delegation; approver chain; roll-up, exit signal and stage outcomes; permissions within the platform ceiling | `op_add_group` / `op_add_user` (Matrix roles are fixed tiers) |
| `validate`, `diff` | local checks (schema, v5 findings, app parity) + `POST …/releases/validate`; v5's draft-vs-live list | `validate`, `check` |
| `publish`*, `release_status` | see below; `resend_live` re-sends a lost hand-off | `op_publish` |
| `migrate_running` | stub: explains running cases stay pinned until the G3 admin action; left for the lead to wire to G3's API | `op_migrate_running` |

\* Destructive ops are dry runs unless `confirm: true`. Every write refuses new broken-flow findings (gate cycle,
dead gate, unreachable outcome, stage without approver, key collision) unless `allow_new_findings: true`.

**Publish** follows the same order as the in-app portal:
1. **Checks.** A reason is required. v5 error findings block unless `accept_findings`. Local app-parity errors and the
   app's dry run must also pass.
2. **Provisioning on the first publish** (`provision.admin_email`, plus company, name and seats). It returns the
   workspace code, the login link and the **one-time setup code**, with a "share privately, shown once" warning.
3. **v5 publish bookkeeping** is written to the draft store, conflict-safe.
4. **`POST …/releases`** with v5's post-publish manifest and `source_ref = configurator:<ref>@v<N>`.
   - If the app refuses, the draft bookkeeping is rolled back when nobody has saved since.
5. **The design-time ledger** `cfg_releases` is appended, as the browser bridge does.

**App client.**
- The admin token is cached in memory only, with one re-login on 401. Sign-in is limited to 10 per 5 minutes and that
  limit is shared with F4b, so a 429 is reported, never looped.
- It rides out a backend restart (~16 s backoff; asked for by the lead because of G3).
- It never re-sends a provision or publish that the app may already have seen.

Not built: `start_case` / `case_status`. They need a workspace user's token (a claimed BA account).

## MCP tools
There are 27 tools, one per op with the same names. Each carries `readOnlyHint` / `destructiveHint` annotations, and
the server sends instructions describing the model, the typical loop and the rules (ask the human when the brief is
ambiguous; the human decides to publish; the setup code is a secret).

The input schemas are the same JSON Schemas the CLI validates. That is why the server uses the SDK's low-level
`Server`; `McpServer` would need every schema re-declared in zod.

## Wiring into Claude Code (the user's settings were not edited)
- **Option 1:** copy `agent-configurator/.mcp.example.json` into the project's `.mcp.json`. It runs `node …/mcp-server.mjs`
  with `MATRIX_APP_ENV_FILE` pointing at the sandbox `app/backend/.env`; only the two platform-admin keys are read.
- **Option 2:** run
  `claude mcp add matrix-workspace-configurator -e MATRIX_APP_ENV_FILE=…/app/backend/.env -- node …/agent-configurator/mcp-server.mjs`.

Then give it a plain-language brief. Add `CFG_PROTECTED_WORKSPACES=ws_aditya_test` if the agent must never touch that
workspace. The same ops are available in a shell via `node agent-configurator/bin/cfg.mjs <op> --json '{…}'`.
