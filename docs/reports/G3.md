## #2 — Migrate running cases (platform admin)

### How it works
- **API:** `POST /api/platform/workspaces/{ref}/migrations`
  - Body: `{from_release_version: N | "all_older", to_release_version (default live), scope: {module_keys, site_ids, record_ids}, reason, dry_run (default true), stage_map?, restart_stage_on_chain_change?}`.
  - Also `GET …/migrations` and `GET …/migrations/{id}`.
- **Dry run:** for each case it reports:
  - compatible or blocked, with the reasons;
  - the stage before and after, and the stage mapping with how each stage was matched (`same`, `by_name`, `by_order`, `explicit`, `unmapped`);
  - fields kept, dropped, changed kind, or newly required;
  - how many approvals are carried over.
- **Execute:** needs a reason.
  - One locked transaction per **site**: the site row and its records are locked `FOR UPDATE`, and every running case is re-checked under the lock.
  - If any running case on a site is incompatible, the whole site is skipped. A site is never half-migrated.
  - The full pre-migration `runtime_state` is kept twice: in the append-only journal and in the audit provenance.

### What moves, and why both
- The runtime reads a case's rules from `module_records.release_id`. A new case on a site starts from `sites.config_release_id`.
- F2's guards require the record's release to equal the site pin on every write.
- So the migration moves the **site pin and every running custom-module case on that site** together.
- Finished cases keep the release they finished on. The guard now checks "record = site pin" only on insert or on a release change.
- A running case of another module on the same site moves too. It is reported as `co_migrated`.

### Controlled re-pin path (DB)
- F2's free `matrix.allow_repin=on` switch is gone.
- The pin triggers accept a move only when all of these hold:
  - the transaction-local `matrix.release_migration` setting names a *running* `module_release_migrations` row of the same tenant;
  - an append-only `module_release_migration_items` row authorises exactly that site or record moving from → to (`cfg_release_migration_authorizes`).
- Plain UPDATEs, the old switch, and forged or finished migration ids are refused. The smoke proves each of these with direct SQL.

### Audit
- **Per case:** a `module_release_migrated` row, which appears in the case's audit trail. Its provenance holds `{from_release, to_release, actor (platform-admin email), reason, before_stage, after_stage, stage_mapping, fields, approvals_carried, pre_state}` and a hash-chained `release_migrated` runtime event. `audit_chain_valid` stays true across releases.
- **Per site:** a `site_release_migrated` row.
- **Per run:** a `release_migration_executed` row.
- Approvals are append-only and stay as history on the old release.

### Compared with operaton-plat
- `op_migrate_running` moves every instance of an older definition in one shot: no dry run, no reason, no per-case report.
- Ours adds a dry run, an explicit stage mapping, a compatibility report, per-site atomicity, a journal and an audit trail.

### UI
`/#/admin` → **Workspaces** → **Provisioned workspaces** → **Details** → **Migrate running cases**:
1. Choose from / onto / modules / the restart option.
2. **Dry run** → compatibility table.
3. Enter a mandatory reason.
4. "Migrate N cases…" → **Confirm migration**.
5. Results, then **Earlier migrations**.

The case page shows "Moved to another release · v1 → v2 · stage … · reason".

## #3 — "Only for sites they created"

### The rule
- **Manifest:** stage-level `restricted_to: "site_creator"`. It is optional; absent means today's behaviour. Publish accepts it through the app's schema copy. Any other value is a `schema` error.
- **Warnings:**
  - `creator_rule_first_tier`: the chain does not start with the executive.
  - `creator_rule_builtin_ignored`: the rule is set on a built-in module.
- **Creator** = `sites.submitted_by` OR `sites.assigned_to`. This is the real app's two-person identity (`_assert_is_site_creator`, `assert_executive_owns_site`), so a BD reassignment hands the right over.
- **Applies to:** the stage's **first step** only.

| Who acts on the creator step | Result |
|---|---|
| An executive who doesn't own the site, even with a delegation | **403 `not_site_creator`** |
| A supervisor who doesn't own the site | **403 `not_site_creator`** |
| The owner, executive or supervisor (real E1) | Acts. **No delegation needed.** |
| A business admin who doesn't own the site | Acts **only as a flagged override**: `is_override=true`, provenance `override` + `creator_override` |

Later steps are unaffected.

### Mapping and deviations
- **Deliberate deviation from real-app E4:** in the real Launch creator review the business admin gets no bypass. Ours follows F2's ruling that the generic runtime records overrides rather than hiding them.
- The operaton-plat equivalent is `"assignee":"initiator"`. It has no hand-off and only hides tasks.
- Ours also widens **list and detail visibility:** an executive sees cases on sites they own when the module has a creator-scoped stage. That case appears in their "My cases".

### Enforcement
- **Runtime:** `allowed_actions` and the action endpoint.
- **DB:** the `module_approvals` guard (`20261005_2`) refuses a non-owner row on the creator step unless it is a flagged business-admin override. The smoke forges such a row directly in SQL and it is refused.

### Designer
In-app configurator copy only (`app/frontend/public/configurator/configurator.dc.html`, 54 lines; `web/` untouched):
- a per-stage **"Only the site’s creator can do this"** toggle in the wizard's Stages step;
- the same toggle on the inspector's stage cards of custom modules;
- v5 state `stage.creatorOnly` ⇄ manifest `restricted_to`;
- a publish-diff entry "creator rule".

### UI
The case page shows:
- "Only the site’s creator can do this step … That’s you.";
- "it waits for the site’s creator";
- the BA override wording;
- "site creator only" on stages and in lists.

## #4 — Role-scoped saved views

### Data
- **Table:** `module_views` (`20261005_3`, RLS `tenant_isolation`).
  - Columns: tenant, module (NULL = all custom modules), name, filter, columns, audience roles, position, is_default, seed_key, created_by.
  - Delete is a soft delete.
- **Default views:** seeded by the DB for every enabled custom module. A `tenant_modules` trigger does it on publish, and existing modules were backfilled.

| View | Audience | Default for |
|---|---|---|
| Awaiting my approval | executive, supervisor | executive, supervisor |
| Admin sign-off | business admin | business admin |
| My cases | executive, supervisor | — |
| Team queue | supervisor, business admin | — |
| All cases | everyone | observer |
| Closed | everyone | — |

- **Reset:** `POST …/views/reset` drops the module's views and re-seeds the defaults.

### API
- `GET /m/{key}/views[?manage=true]`
- Business-admin CRUD: `POST`, `PATCH`, `DELETE /m/{key}/views[/{id}]`.
- `GET /m/{key}/records?view=<id>`:
  - Scope comes **first**: the tenant, then for executives the cases they opened, are assigned, are delegated, or own under a creator-scoped stage.
  - The filter is applied on top, so a view can only narrow.
  - A view outside your audience, module or tenant returns 404.
  - Filters reject unknown keys (`extra="forbid"`), so a crafted `{tenant_id, role}` gets 422.
- **Filters:** stage, status, closed, assigned_to_me, created_by_me, mine, awaiting (my_tier/tier), actionable, assigned, site_ids, kind.

### Mapping
- operaton-plat's My tasks, Team queue and Admin approvals are Tasklist filters with per-group READ grants. Ours are rows with audience roles.
- G2's rules are kept: audience is not access, and the effective runtime role decides.

### UI
- **`/#/m/<key>`:** a view switcher with per-view counts and a description line, and per-view columns. The sidebar's Queue / Awaiting approval / History links map onto the seeded views.
- **Business admins:** a **Manage views** button → `/#/m/<key>/views` to create, edit, remove, or reset to defaults.

Their substance:

```sql
-- 20261005_1  (journal + the only re-pin path)
CREATE TABLE module_release_migrations (id uuid PK, tenant_id uuid NOT NULL → tenants ON DELETE CASCADE,
  to_release_id uuid NOT NULL, from_spec text CHECK (~ '^(all_older|v[0-9]+)$'), scope jsonb, reason text CHECK (length(btrim)>=3),
  actor text NOT NULL, status text CHECK IN ('running','done','failed') DEFAULT 'running', summary jsonb, created_at, finished_at,
  FK (tenant_id, to_release_id) → tenant_config_releases(tenant_id, id));             -- + guard: only status/summary/finished_at, only while running
CREATE TABLE module_release_migration_items (id uuid PK, migration_id → module_release_migrations ON DELETE CASCADE,
  tenant_id, site_id → sites ON DELETE CASCADE, record_id → module_records ON DELETE CASCADE NULL (= site pin item), module_key,
  from_release_id, to_release_id (both FK (tenant_id, id) → tenant_config_releases), before_stage, after_stage,
  before_state jsonb /* full pre-migration runtime_state */, after_state, plan jsonb, created_at,
  CHECK ((record_id IS NULL) = (module_key IS NULL)), CHECK (from_release_id <> to_release_id));   -- + insert guard + cfg_forbid_mutation (append-only)
CREATE FUNCTION cfg_release_migration_authorizes(tenant, site, record, from, to) -- running migration named by
  current_setting('matrix.release_migration') + an item for exactly this move
-- cfg_sites_pin_release / cfg_module_records_guard: re-pin ONLY when authorised (matrix.allow_repin removed);
-- record = site pin checked on INSERT and on a release change only.
-- RLS tenant_isolation on both tables; REVOKE ALL FROM anon, authenticated.

-- 20261005_2  (creator rule in the approvals guard)
CREATE FUNCTION cfg_user_owns_site(site, user) = sites.submitted_by = user OR sites.assigned_to = user;
-- cfg_module_approvals_guard: entitled := entitled AND owns() on chain[1] of a stage with restricted_to='site_creator'

-- 20261005_3  (saved views)
CREATE TABLE module_views (id uuid PK, tenant_id → tenants ON DELETE CASCADE, module_key text NULL,
  name text CHECK 1..80, filter jsonb object, columns jsonb array, audience text[] ⊆ {executive,supervisor,business_admin,observer},
  position int, is_default bool, seed_key text, created_by → users ON DELETE SET NULL, created_at, updated_at, deleted_at,
  FK (tenant_id, module_key) → tenant_modules ON DELETE CASCADE);  UNIQUE (tenant_id, module_key, seed_key) WHERE seed_key IS NOT NULL;
CREATE FUNCTION cfg_seed_module_views(tenant, module);  -- 6 defaults, ON CONFLICT DO NOTHING
CREATE TRIGGER trg_tenant_modules_seed_views AFTER INSERT OR UPDATE OF enabled ON tenant_modules;  -- custom+enabled ⇒ seed
SELECT cfg_seed_module_views(tenant_id, module_key) FROM tenant_modules WHERE kind='custom' AND enabled;  -- backfill
-- RLS tenant_isolation; REVOKE anon/authenticated.
```

## Remaining gaps (for F5)

**Migration**
1. **Idle pinned sites:** a site with no running case is not re-pinned. A case opened on it later still starts on the old release. An "include idle sites" option would fix this.
2. **Crash mid-run:** the header stays `running`. Sites already committed are consistent; the rest are untouched.
3. **Dropped field values:** values for fields the target lacks are removed from the live case and kept only in the journal and audit. There is no restore UI.
4. **G1 integration:** G1's `migrate_running` stub should call §1.1 of `docs/G3-API.md` (dry run, then confirm with a reason).
5. **G1 schema:** G1's schema (building-blocks `manifest.schema.json`) does not know `restricted_to` yet. The app's copy does.

**Creator rule**
6. **Deliberate deviation:** the business-admin override on creator steps departs from real E4 (no bypass in Launch). A strict variant could be a second enum value.
7. **Effective role:** the generic runtime uses the module-membership tier, not the effective role after `X-Override-Role`. A business admin simulating an executive is still treated as business admin, and a supervisor that has dropped to executive is still a supervisor. This is F4a semantics, which differ from G2's E3.
8. **Scope level:** the rule is stage-level. G2's module-level `executive_scope` (creator / delegation / creator_or_delegation) is not built.
9. **Built-ins:** the rule is not applied to built-ins. They keep their bespoke checks.

**Views**
10. **Performance:** view filters run in Python over the scoped rows. The UI makes one list call per view to show counts. Fine for the sandbox; the real project should push filters into SQL and paginate.
11. **Missing features:** there are no personal (per-user) views.

**Configurator**
12. **Standalone copy:** the standalone `web/` configurator keeps `creatorOnly` in shared drafts but doesn't show or emit it.

**Environment**
13. **Rate limits:** restart the backend between smoke runs (in-memory auth rate limits).
14. **SEC-1** is still open (the smokes use the code-less first-password path for staff, as before).
