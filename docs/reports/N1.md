# N1: NocoBase made visible (admin pages, workflow, read-only role)

**Problem.** Signing in at http://localhost:13000 showed nothing from this project. NocoBase 2.2.20 held the
data, but `desktopRoutes` was empty: there was no menu and no page.

**Result.** The data is now visible and in use through NocoBase's own components:

* a **Matrix Configurator** menu with 7 read-only pages that show the real data
* a **Workflow** that writes an activity entry for every publish
* an **ACL** role, `configurator_viewer`, that can see the data but cannot change it

All three are provisioned by idempotent, zero-dependency scripts. Community edition only.

## What you can see now, and where

Sign in at **http://localhost:13000** as root (credentials in the project `.env`). The top bar has a group
**Matrix Configurator**; its pages are in the left sidebar.

| Click path | URL (stable) | Content (real rows) |
|---|---|---|
| Matrix Configurator → Overview | `/admin/mcfg-overview` | what NocoBase stores for the configurator, the read-only rule, links |
| → Workspaces | `/admin/mcfg-workspaces` | 5 `cfg_workspaces` rows: name, slug, custom?, live/draft version, last updated. Click the **name** or **View** to open a read-only drawer with all fields and the `state` JSON |
| → Releases | `/admin/mcfg-releases` | 2 `cfg_releases` rows, newest first, with a workspace filter. Click the **version** or **View** to open a drawer with the `manifest` JSON |
| → Modules / Gates / Stages | `/admin/mcfg-modules`, `/admin/mcfg-gates`, `/admin/mcfg-stages` | 55 / 56 / 147 projection rows, each with a filter form (workspace slug + kind/status, from/to, module key) and a drawer showing the `data` / `condition` JSON |
| → Activity | `/admin/mcfg-activity` | `cfg_activity`, written by the workflow |
| ⚙ → Workflow → "Matrix Configurator · Release published → activity log" → Configure | `/admin/settings/workflow/workflows/<id>` | canvas: Collection event → Query record → Create record. The **Executed** count shows the run history |
| ⚙ → Users & Permissions → Roles & Permissions → Configurator viewer | `/admin/settings/users-permissions` | the read-only role (Data sources, Desktop routes) |

Each page offers only **Filter / Refresh / View**. There are no add, edit, delete, bulk or row-selection
controls, because the configurator owns every write.

## How it is provisioned (all idempotent; second run prints "no changes — already provisioned")

| Script | Does |
|---|---|
| `nocobase/scripts/provision-workflow.mjs [--prove] [--no-backfill] [--revise]` | creates the collection `cfg_activity` (defined as `ACTIVITY_COLLECTION` in `lib/schema.mjs`; it is **not** in `COLLECTIONS`, so `provision.mjs`, `reset.mjs` and the client are unchanged) and the workflow, then backfills existing releases through the same workflow (`workflows:execute`) |
| `nocobase/scripts/provision-ui.mjs [--force] [--only=…] [--remove]` | creates the menu group and 7 pages from `nocobase/lib/ui-spec.mjs` |
| `nocobase/scripts/provision-acl.mjs [--test-user] [--no-verify]` | creates the role, its table and route permissions, and optionally the test user; then checks the role live as that user |
| `npm run provision:all` (in `nocobase/`) | runs `provision.mjs` → workflow → ui → acl, in that order |

**Workflow (community Workflow plugin).**

* **Trigger:** collection event on `cfg_releases`, after a record is added (`mode: 1`), **async**. A condition skips `workspace_slug` values that contain `__smoke`, so `smoke.mjs` leaves no activity rows behind.
* **Node 1, Query record:** looks up `cfg_workspaces` by slug.
* **Node 2, Create record:** writes `cfg_activity` with event, summary, workspace slug and name, version, reason, published_by, release_id and published_at.

I did not keep a "last published" field on `cfg_workspaces`. Adding one would change a contract collection, bump its `updatedAt`, and race with configurator saves.

**ACL.** Role `configurator_viewer`:

* snippets `!pm !pm.* !ui.*`, so no settings, plugin manager or UI editor
* `allowNewMenu: false`, and the global table strategy for `main` allows no actions
* independent permission **view** (all fields) on the 6 `cfg_*` collections
* menu access to the group, its 7 pages and their 7 tabs only

The test user `configurator-viewer` has only this role. Its credentials are in the gitignored `.env` (`NOCOBASE_VIEWER_*`) and have never been printed.

## NocoBase 2.x mechanisms used (checked in the v2.2.20 source and on the live instance)

* **Pages** are 2.x "modern" flow-engine pages. Each is a `desktopRoutes` row of `type: 'flowPage'` (plus a hidden `tabs` child) under a `group` route. Its content is a `flowModels` tree: `RootPageModel → RootPageTabModel → BlockGridModel → FilterFormBlockModel / TableBlockModel (TableColumnModel, TableActionsColumnModel → ViewActionModel)`. Popups are `ChildPageModel → DetailsBlockModel → DisplayJSONFieldModel`.
* They are written through the **`flowSurfaces` server API** (`plugin-flow-engine/src/server/flow-surfaces/`, which is also what NocoBase's own UI-builder skill uses), in four steps:
  1. `createMenu{type:'group'}`
  2. `createPage{pageSchemaUid:'mcfg-…', pageUid, tabSchemaUid}`. Fixed uids give stable URLs and deterministic trees: 418 `flowModels` rows after every rebuild.
  3. `applyBlueprint{mode:'replace'}`
  4. `removeNode`
* Source finding (`flow-surfaces/default-block-actions.ts`): `applyBlueprint` **always** injects addNew / bulkDelete / edit / delete into tables, and edit into details blocks; there is no public way to turn this off. The blueprint therefore declares the actions that open popups with `popup.tryTemplate:false`, so no popup templates are auto-generated (0 templates exist). The script then removes every top-level action whose model is not Filter / Refresh / View / FilterForm* (6 per page).
* `mode:'create'` auto-saves inline popups as reusable templates, so I used `replace`. Each page route stores a spec hash in `desktopRoutes.options.matrixConfigurator`. A page is rebuilt only if its spec changed or the live page is no longer read-only, for example after someone adds a button in the UI editor. `--remove` cleanly deletes everything: `flowModels` went to 0, and a rebuild from scratch took 43 s.
* **Workflow API:**
  * `workflows:create`, then `workflows/<id>/nodes:create` (node 2 refers to node 1's `{{$jobsMapByNodeKey.<key>.name}}`), then `workflows:update{enabled}`
  * an executed version is immutable, so `--revise` uses `workflows:revision{filter:{key}}`
  * manual run: `workflows:execute?filterByTk=<id>` with body `{data:<releaseId>}`. The body *is* the trigger context: if it is wrapped in `{values:…}`, the trigger silently loads the **first** release. I hit this once (below).
* **ACL API:** `roles:create`, `dataSources/main/roles:update{strategy}`, `roles/<r>/dataSourceResources:create|update{usingActionsConfig, actions:[{name:'view', fields}]}`, and `roles/<r>/desktopRoutes:set`.

## Limits and things the community edition can't do here

* NocoBase 2.2.20 tables have **no row-click event**, so "row click" is a clickable title column plus a **View** action. Both open the same read-only drawer.
* **No "read-only page" switch exists.** Read-only comes from removing the injected actions, plus ACL for non-root users. Root can still turn on the UI editor and add buttons by hand; the next `provision-ui` run detects this and rebuilds the page.
* **The workspace filter is a free-text input,** because `workspace_slug` is a plain string. A dropdown would need a relation field on the `cfg_*` collections, which I was not allowed to change.
* **Drawer header text:** the drawer header shows the tab title "Details", not the popup title.
* **Approval UX** (the Workflow: Approval plugin) is commercial (Professional) and was not touched. No commercial plugin was enabled or attempted. The pre-enabled `license` plugin was left as found.
* **Other roles also see the menu:** the default `admin` and `member` roles have `allowNewMenu: true`, so NocoBase also gave them the new menu. The sign-in page offers **"Create an account"** (sign-up is on by default, and new users get `member`). This is harmless here: the instance is bound to 127.0.0.1, and `member` only has `view:own`, so it sees no cfg rows. Turn sign-up off before exposing the instance.
